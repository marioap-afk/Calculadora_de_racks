# Agent Execution, Model Routing & Prompting Protocol

Workflow:
V2

Archetype:
FOUNDATION EVOLUTION

Goal:
Crear un protocolo estable para que un Coordinator pueda delegar gates de
implementación a un Execution Controller (Codex), y éste pueda seleccionar
dinámicamente:

- executor;
- model;
- effort;
- prompt profile;
- transport;

y delegar trabajo a Claude/Codex workers con handoffs estructurados,
exact-SHA y STOP conditions.

Esta iniciativa modifica el PROCESO DE DESARROLLO de RackCad.

No modifica funcionalidad de producto.

======================================================================
MOTIVATION
======================================================================

Current problems to solve:

1. powerful models are used for routine work;
2. model/effort selection is informal;
3. Coordinator prompts still require manual transfer;
4. implementation gates require repeated human relay;
5. Computer Use is possible but fragile as the primary inter-agent bus;
6. handoffs should be machine-readable and exact-SHA attributable.

The new protocol must reduce manual execution overhead without moving
architectural or product authority away from Coordinator/Architect/Owner.

======================================================================
DELIVERABLE B — MODEL / EFFORT ROUTER
======================================================================

Do not hardcode one model for all work.

Define a stable routing policy based first on TASK CLASS.

At minimum classify:

- mechanical implementation;
- repetitive propagation/wiring;
- test implementation;
- documentation;
- characterization;
- debugging;
- uncertain root-cause investigation;
- cross-layer implementation;
- architecture review;
- adversarial conformance;
- long-running agentic implementation.

For each task profile evaluate:

- ambiguity;
- architecture sensitivity;
- breadth;
- expected tool use;
- failure cost;
- mechanical repetition;
- expected horizon.

Then select:

Executor
Model
Effort
PromptProfile

Separate:

MODEL_ROUTING
= stable selection principles

from:

MODEL_CATALOG
= current available models and recommended mappings

The catalog must be updateable without changing Workflow.

Do not assume Opus or any specific model remains permanently preferred.

======================================================================
EFFORT POLICY
======================================================================

Define effort levels semantically rather than by vendor-specific labels alone.

Example mapping:

Routine
Balanced
Deep
Long-horizon
Maximum

MODEL_CATALOG can map those to current provider controls.

Define escalation.

Example concept:

routine model / balanced
→ stronger effort
→ stronger model
→ long-horizon
→ maximum only when justified

No requirement to traverse every level.

Every upward escalation should have:

MODEL_ESCALATION_REASON

Avoid silently converging to the strongest model for all tasks.

Also allow DOWN-ROUTING:

a hard gate may use a strong model for diagnosis,
then a cheaper/faster model for mechanical implementation/docs.

======================================================================
DELIVERABLE F — TRANSPORT HIERARCHY
======================================================================

Define preferred communication mechanisms in this order:

1. filesystem + structured artifacts;
2. CLI / direct agent invocation when available;
3. connector/API/MCP equivalent where stable;
4. Computer Use as fallback;
5. manual user relay as final fallback.

Computer Use must NOT be the normative primary message bus.

Computer Use is appropriate for:

- AutoCAD;
- GUI-only host verification;
- visual inspection;
- agents without machine-readable interfaces.

The protocol must remain the same regardless of transport.

======================================================================
DELIVERABLE G — EXECUTION CONTROLLER
======================================================================

Define Codex Execution Controller responsibilities:

1. receive Gate Contract;
2. read current repo authority;
3. classify task;
4. select executor/model/effort/profile;
5. create delegation packet;
6. verify exclusive write ownership;
7. invoke worker;
8. receive handoff;
9. independently inspect:
   - SHA;
   - git status;
   - diff;
   - allowed scope;
   - tests;
   - evidence;
   - invariants;
10. classify execution:
   - VERIFIED;
   - REWORK REQUIRED;
   - BLOCKED;
11. route corrections if authorized;
12. hand result back to Coordinator.

Codex must not silently expand architecture or product scope.

======================================================================
REWORK POLICY
======================================================================

Default:

MAX_REWORK_LOOPS = 3

But define "same failure class".

Do not count a completely new unrelated defect as merely another retry
without analysis.

On repeated failure:

STOP
→ root-cause investigation
→ Coordinator.

Do not endlessly rewrite prompts.

======================================================================
STOP CONDITIONS
======================================================================

At minimum:

- Owner Validation required;
- architecture outside Freeze;
- material ambiguity;
- contradictory evidence;
- destructive/irreversible action not authorized;
- missing credentials/permissions;
- conflict with another active owner;
- branch/worktree ownership conflict;
- dependency not integrated;
- required AutoCAD/user interaction;
- repeated rework limit reached;
- Worker loses context or cannot verify authority revision;
- main movement invalidates exact-SHA assumptions;
- initiative contract explicitly says STOP.

On STOP:

no speculative continuation.

Return structured blocker to Coordinator.

======================================================================
OWNERSHIP
======================================================================

Never allow two workers to write simultaneously to:

- same worktree;
- same branch;
- same mutable artifact set.

Each delegation must establish:

OWNER
BRANCH
WORKTREE
BASE_SHA
ALLOWED_WRITE_SCOPE

Decision authority returns to Codex after worker handoff.

Gate authority remains with Coordinator.
