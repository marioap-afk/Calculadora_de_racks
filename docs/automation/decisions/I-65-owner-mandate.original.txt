- automatización de análisis;

- integración bidireccional.

Discovery debe verificar las capacidades reales de la versión disponible.

GOAL
======================================================================

Create a provider-neutral Structural Analysis Interop foundation and the
first RAM Elements adapter.

Preferred architecture:

RackCad Product Model
        ↓
Structural Analysis Model
        ↓
RAM Elements Adapter
        ↓
RAM Elements

RAM Elements should be a derived analysis consumer, not a persistence
authority for RackCad.

======================================================================
CORE PRINCIPLE
======================================================================

RackCad / DWG
= product/design authority

Structural Analysis Model
= derived neutral analytical representation

RAM Elements
= external analysis consumer

It must remain possible to regenerate the analysis model from RackCad.

RackCad must not require a RAM file in order to reconstruct or open the
rack correctly.

======================================================================
TRANSPORT PRIORITY
======================================================================

Preferred:

1. supported API/SDK;
2. supported machine-readable interchange;
3. documented CLI/batch interface;

Do not automate mouse clicks merely to simulate an API without first
establishing that no better supported mechanism exists.

======================================================================
EQUIVALENCE TARGET
======================================================================

The first meaningful success criterion is NOT:

"RAM opens a file."

It is:

A model generated from RackCad is structurally equivalent, under the frozen
mapping contract, to a reference model created manually in RAM Elements.

Define an equivalence matrix covering relevant facts such as:

- node coordinates;
- connectivity;
- member type;
- local orientation;
- section;
- material;
- releases;
- supports;
- load values;
- load locations;
- combinations if in scope.

Owner/engineering validation must compare the generated model against a
known manual reference.

======================================================================
UNITS
======================================================================

Treat units as a critical contract.

RackCad may use inches or other internal/product units.

RAM may use another unit system.

Do NOT scatter conversion constants through mappings.

Define one explicit structural-unit boundary.

Every transferred quantity must have known dimensions, including as applicable:

- length;
- area;
- force;
- moment;
- stress;
- mass;
- density;
- distributed load.

Adapter performs provider-specific conversion.

Require tests designed specifically to detect:

- inch/mm errors;
- lb/N or kgf/N confusion;
- distributed-load scaling;
- moment-unit scaling.

Fail closed on unknown units.

======================================================================
SECTIONS
======================================================================

A RackCad component name is NOT automatically a structural section.

Discovery must characterize current profile authorities.

Define explicit mapping:

RackCad profile identity
        ↓
StructuralSection
        ↓
RAM section representation

StructuralSection should contain the actual properties required by the chosen
analysis strategy.

Do not use display strings as primary identity.

Determine whether RAM can consume:

- catalog sections;
- user-defined sections;
- parametric shapes;
- arbitrary section properties.

Do not fabricate unavailable section properties.

======================================================================
MATERIALS
======================================================================

Define explicit structural material mapping.

Do not infer properties merely from product names.

Characterize what RackCad currently knows and what must come from a structural
engineering catalog/configuration.

Examples potentially needed:

E
G
Poisson ratio
density
yield strength

Only include properties required by the frozen slice.

Keep product material identity distinct from provider-specific RAM material
identity.

======================================================================
MEMBER IDEALIZATION
======================================================================

This is an architectural decision.

RackCad geometry represents physical product geometry.

Structural analysis may require analytical centerlines / member idealization.

Freeze must define:

- analytical node locations;
- eccentricities;
- centerline conventions;
- member endpoints;
- offsets;
- local axes;
- member orientation;
- connectivity tolerances.

Do NOT simply export visible CAD line endpoints unless those are proven to
represent the analytical model.

======================================================================
CONNECTIONS / RELEASES
======================================================================

Rack connections may not be equivalent to fully fixed or fully pinned joints.

Discovery must identify what the current product/domain knows versus what must
be introduced as explicit structural-analysis assumptions.

Do not silently select fixed/pinned releases because they are convenient.

If connection stiffness/semi-rigidity is not available in V1:

record the explicit analysis assumption and scope limitation.

======================================================================
SUPPORTS
======================================================================

Define how base/support conditions are represented.

Do not infer foundation/losa stiffness unless explicitly modeled.

V1 may use a controlled support assumption for equivalence testing, provided
it is explicit.

Future anchor/slab modeling is separate unless Freeze explicitly includes it.

======================================================================
LOADS
======================================================================

Separate:

PRODUCT FACTS
from
STRUCTURAL LOAD MODEL.

For example:

pallet mass/weight
≠ automatically
analysis nodal load.

Define a structural-load translation layer.

Questions include:

- tributary distribution;
- point vs distributed load;
- load direction;
- dead/live/storage categorization;
- impact/dynamic factors;
- seismic mass;
- self-weight;
- combinations.

Do NOT introduce engineering assumptions invisibly.

For the first slice, keep load scope intentionally small and auditable.

======================================================================
LOAD COMBINATIONS
======================================================================

Do not implement a complete design-code engine in this initiative unless
Discovery proves one already exists and can be reused.

If load combinations are required for the pilot:

use a small explicitly frozen reference set.

RMI/AISC/seismic/code-level automation is a future structural-design layer
unless explicitly claimed.
