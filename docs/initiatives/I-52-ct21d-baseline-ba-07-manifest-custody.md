## 1. Purpose and threat model

The manifest attests the **enumerable known set** of loaded code (E-10) and the managed set (E-11M) and the profile values (E-13); it proves **no isolation** (`NG-13..NG-18`). This procedure gives the manifest **audit integrity**.

| Property | Statement |
|---|---|
| **tamper evidence** | **yes**: accidental change, unrecorded change and rewriting of the custody chain are detectable |
| **non-repudiation and signer identity** | **no**: there is no cryptographic signature and no proof of who acted |
| out of the threat model | a hostile local administrator (`NG-13`); self-review by one person is a declared limit |

## 2. Manifest layers and what is stored where

The manifest has three layers (Proposal V2 section 14): **build-bound**, **machine-profile-bound**, **session-evaluated**.

| Layer | Content | May it be in the repository? |
|---|---|---|
| build-bound | modules of the build and their SHA-256 | yes, the layer and its hash |
| machine-profile-bound | modules of the machine profile (drivers, security software), OS and profile identity | **no**: it stays with the machine's evidence |
| session-evaluated | the run's snapshots | no; it belongs to the run evidence |

The repository may hold the **hashes** of the manifest and the build layer, never the machine layer.

## 3. Capture procedure (control plane; not executed here)

1. The Coordinator **authorizes** the capture in writing (a custody-log entry).
2. The **control plane** starts a **fresh** controlled session on the exact build, machine and profile.
3. The control plane runs the **warm-up** (BA-09) and then the E-10 enumerations and the hasher; the manifest is **generated by the control plane** and is **never hand-edited**.
4. The control plane serializes the manifest **canonically** (section 4) and computes its SHA-256; that hash is the **manifest identity**.
5. The manifest is written to **content-addressed, read-only** storage (section 5).
6. The control plane writes a `CAPTURED` custody entry (section 6).

## 4. Canonical serialization and hash

| Aspect | Rule |
|---|---|
| format | JSON, UTF-8, LF line endings, no BOM |
| keys | sorted, ordinal |
| numbers | exact: integers in decimal; doubles as in BA-05 section 2.1 if any occur |
| arrays | in the declared order of the schema (module lists sorted by normalized full path, ordinal) |
| hash | SHA-256 of the serialized bytes, lowercase hexadecimal; this is the **manifest identity** |
| association with the tuple | the manifest hash is a tuple field; a run whose recorded hash differs from the baseline hash is `INVALID` |

## 5. Storage, retrieval and versioning

| Aspect | Rule |
|---|---|
| storage | content-addressed and read-only: `manifest-<hash>.json` in a designated evidence location outside the product binary; the machine-profile layer stays with the machine's evidence |
| retrieval | by hash; the hash is **verified on read**; a mismatch refuses use |
| amendment and versioning | a manifest is **never edited**: a change is a **new capture with a new hash** and a `supersedes: <hash>` link; adding a module entry follows the transitions of section 7; superseded manifests are retained |

## 6. Hash-chained custody log

An **append-only** log records each capture, review, approval, anchoring, use, supersession and revocation.

### 6.1 Entry (normative fields)

| Field | Content |
|---|---|
| `index` | integer, 0 for the genesis entry |
| `utc` | UTC time of the entry |
| `role` | `CAPTURE_ROLE`, `REVIEW_ROLE`, `APPROVAL_ROLE` or `CUSTODY_ROLE` |
| `actor` | the actor of the entry (a person or `CONTROL_PLANE:<id>`) |
| `event` | `AUTHORIZED`, `CAPTURED`, `REVIEWED`, `APPROVED`, `ANCHORED`, `IN_USE`, `SUPERSEDED`, `REVOKED` |
| `manifestHash` | the manifest identity concerned |
| `prevEntryHash` | the `entryHash` of the previous entry; the genesis entry uses 64 zero digits |
| `anchorRef` | for `ANCHORED` entries: the remote reference of section 8; otherwise `null` |
| `note` | free text, may be empty |
| `entryHash` | SHA-256 of the canonical serialization (section 4) of **all other fields** of the entry |

### 6.2 Verification algorithm

1. Recompute every `entryHash` from the other fields; a difference is a **broken entry**.
2. Check that each `prevEntryHash` equals the `entryHash` of the entry with the preceding `index`; a difference is a **broken chain**.
3. Compare the head `entryHash` with the **anchored** head (section 8); a difference means the log was rewritten after the anchor.
4. Check the state machine of section 7 for every manifest: an illegal transition is a **violation**.

## 7. Roles and transitions

| Role | Holds | May not |
|---|---|---|
| `CAPTURE_ROLE` | runs the capture procedure **through the control plane** and submits the manifest | approve its own capture |
| `REVIEW_ROLE` | the Owner or CAD manager (or a delegate they record) who checks the machine-layer entries (drivers, security software) and the build layer against the build receipt | capture or approve |
| `APPROVAL_ROLE` | the Coordinator, who approves a manifest hash as the baseline manifest | capture |
| `CUSTODY_ROLE` | keeps the custody log and the external anchor | alter an entry that is already anchored |

```text
CAPTURED -> REVIEWED -> APPROVED -> ANCHORED -> IN_USE -> SUPERSEDED
   any state -> REVOKED   (with a recorded cause)
```

- `CAPTURED -> REVIEWED`: by `REVIEW_ROLE`. `REVIEWED -> APPROVED`: by `APPROVAL_ROLE`, with the manifest hash in the entry. `APPROVED -> ANCHORED`: by `CUSTODY_ROLE` (section 8). A manifest that is not `ANCHORED` cannot be `IN_USE`.
- `IN_USE` is recorded at each use with the run id and the tuple. `SUPERSEDED` and `REVOKED` never return to `IN_USE`.

### 7.1 Multi-role policy (`YES_WITH_ROLE_SEPARATION_IN_LOG`)

One human **may** hold several logical roles. Requirements: **each role transition is a separate log entry**; the **actor is recorded** in every entry; **capture is always generated by the control plane**; the **role multiplicity is disclosed in Owner Act 2** (with the count of entries by actor). Self-review is a declared limit, not a hidden one.

## 8. External anchor (placeholder; nothing is created here)

At baseline preparation the **`MANIFEST_CUSTODY_HEADER_HASH`** (the `entryHash` of the head entry of the log, including the approval entry) is anchored in a **Coordinator-controlled immutable reference that is PUBLISHED at a remote**, not merely a local commit.

| Step | Rule |
|---|---|
| 1 | the `CUSTODY_ROLE` writes the header hash into a **version-controlled authority record** (planned path: `docs/automation/evidence/ct21d-manifest-custody-anchor.json`; **not created by this artifact**) |
| 2 | the record is committed in a **reviewed** commit and the commit is **pushed to the remote** |
| 3 | the presence of the commit at the remote is **verified** (remote name, URL, reference, commit SHA) and recorded in the custody log as `anchorRef` |
| 4 | every later custody event (use, supersession, revocation) is re-anchored in the next baseline or evidence commit |
| 5 | verification recomputes the chain and compares its head with the anchored value |

## 9. Audit integrity: what each check protects

| Change | Detected by |
|---|---|
| a manifest file edited in place | retrieval verifies the hash on read |
| an entry edited in the custody log | recomputation of `entryHash` (6.2, step 1) |
| an entry removed or reordered | chain check (6.2, step 2) |
| the whole log rewritten with a recomputed chain | comparison with the anchored head (6.2, step 3) |
| an illegal role transition | state-machine check (6.2, step 4) |
| a manifest used without approval or anchor | `IN_USE` requires `ANCHORED` |
