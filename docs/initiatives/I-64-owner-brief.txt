======================================================================
GOAL
======================================================================

Convertir RackCad de una colección de ventanas modales/temporales a una
workspace persistente y modeless integrada con AutoCAD.

La workspace debe poder permanecer abierta mientras el usuario continúa usando
normalmente AutoCAD:

- seleccionar objetos;
- zoom;
- pan;
- ejecutar comandos;
- cambiar de vista;
- navegar por el dibujo.

Debe existir sincronización bidireccional:

AutoCAD selection
→ RackCad context

RackCad navigation
→ AutoCAD selection / locate / center

La aplicación debe evolucionar hacia una experiencia tipo inspector/workspace CAD.

======================================================================
PRODUCT DECISION ALREADY MADE
======================================================================

NO LIVE MUTATION.

La edición continúa usando el paradigma actual:

UI edit
→ draft/pending state

NO:
- mutation;
- redraw;
- regen;
- commit;

hasta que el usuario pulse:

ACTUALIZAR

Actualizar debe seguir siendo la frontera explícita de commit.

Cambiar de rack/tab NO aplica automáticamente los cambios.

======================================================================
FUNCTIONAL SCOPE
======================================================================

La arquitectura debe contemplar:

1. Workspace modeless persistente.

2. Integración nativa con AutoCAD, evaluando seriamente PaletteSet.

3. Active-document awareness.

4. Sincronización:
   AutoCAD selection → logical RackId → workspace.

5. Rack navigator:
   - dropdown/list/search;
   - logical rack name;
   - SystemKind;
   - views;
   - status.

6. Acciones:
   - Seleccionar;
   - Ver;
   - Centrar;
   - localizar una vista concreta cuando aplique.

7. Browser-like workspace tabs:
   - rack tabs;
   - preview tab;
   - pinned tabs;
   - close without modifying drawing;
   - dirty marker;
   - lazy loading.

8. Persistent DraftSession por RackId:
   - committed base;
   - draft;
   - dirty;
   - stale/conflict state.

9. Cambio entre racks sin perder drafts.

10. Integración progresiva de los editores existentes:
    - Selectivo;
    - Dinámico;
    - Push Back;
    - Cantilever;
    - Cabecera;
    - Cama.

11. Multi-selection foundation:
    selección grande NO debe abrir N tabs automáticamente.

    Preferir:
    Selection (N)

    como contexto agregado.

12. Preparación para cerrar ID3:
    navegación entre racks;
    sesiones persistentes;
    futuros batch edits.

======================================================================
KEY ARCHITECTURAL BOUNDARY
======================================================================

Debe preservarse:

DWG / authored persisted state
= committed authority

WorkspaceSession
= transient editing state

La workspace NO se convierte en autoridad persistente.

Conceptualmente investigar algo equivalente a:

WorkspaceController
├── WorkspaceDocumentSession
│   ├── RackInventory
│   ├── SelectionContext
│   ├── OpenTabs
│   ├── ActiveTab
│   └── DraftSessions
└── AutoCADEventBridge

Los nombres son hipótesis.

No congelarlos antes de Discovery.

======================================================================
AUTOcad EVENT MODEL
======================================================================

Discovery debe caracterizar qué eventos reales se necesitan y cómo evitar
suscripciones dispersas.

Objetivo preferido:

ONE CENTRAL AUTOCAD EVENT BRIDGE

y no:

cada tab/editor suscribiéndose independientemente.

Auditar como mínimo:

- implied selection changes;
- active document changes;
- command start/end;
- object modification;
- erase;
- undo/redo;
- document close/open;
- current selection;
- external RackCad mutations.

No añadir listeners por rack/tab sin justificación.

======================================================================
RACK INVENTORY
======================================================================

Evaluar una autoridad/runtime index ligero por drawing.

Debe poder alimentar:

- rack dropdown;
- search;
- navigation;
- view lookup;
- selection synchronization.

Metadata típica:

RackId
LogicalName
SystemKind
Views
Status

NO mantener geometría/resolved systems pesados para todos los racks.

Debe evitarse:

drawing changed
→ resolve all racks

Preferir:

invalidate
→ refresh on demand.

======================================================================
TABS / PERFORMANCE CONTRACT
======================================================================

Open Tabs
≠
AutoCAD Selected Racks.

Seleccionar 50 racks NO significa crear 50 editores completos.

Inactive tabs deben ser lightweight.

Preferir lazy editor materialization.

No retener innecesariamente por tab:

- resolved geometry;
- BOM;
- AutoCAD objects;
- transactions;
- full WPF trees;
- duplicate event subscriptions.

Discovery debe proponer y medir una estrategia razonable.

======================================================================
PREVIEW TAB
======================================================================

Evaluar UX tipo Visual Studio/browser:

single-click/select rack
→ preview tab

select another rack
→ replaces preview

double-click / pin / edit
→ persistent tab

Dirty tab:
RackName *

Dirty tabs must never be silently replaced.

======================================================================
MULTI-SELECTION
======================================================================

Primera versión no necesita batch edit completo.

Expected initial behavior:

1 logical rack selected
→ contextual editor

multiple racks selected
→ Selection (N) context
→ summary/navigation

No abrir N rack tabs automáticamente.

El diseño debe permitir que una futura extensión implemente:
common-property multi-edit / batch mutation.

======================================================================
STALE / EXTERNAL CHANGE
======================================================================

Éste es un contrato material.

Ejemplo:

Rack A draft opened from committed revision X.

Another command changes Rack A.

User later presses Actualizar.

RackCad must NOT silently overwrite the newer committed state.

Discovery must define a reliable:

BaseRevision / authored fingerprint / equivalent authority check

so Apply can detect:

MATCH
or
STALE / CONFLICT

and fail closed or request explicit reconciliation.

Do not invent a second persistence authority.

======================================================================
MULTI-DOCUMENT
======================================================================

Workspace may remain alive while AutoCAD changes documents.

Design from the start for:

Document A
→ WorkspaceDocumentSession A

Document B
→ WorkspaceDocumentSession B

Switch active document
→ switch workspace context

Do not mix RackIds/state across documents.

V1 may keep sessions only in memory.

Persistent cross-launch workspace restoration is future scope.

======================================================================
EXISTING EDITORS
======================================================================

Do NOT rewrite every editor immediately.

Discovery must determine the safest migration pattern.

Evaluate:

A. host existing controls/viewmodels inside workspace;

B. extract reusable editor surfaces;

C. adapter layer around existing windows;

D. staged migration.

Avoid six parallel editor rewrites.

Existing standalone RACKEDITAR behavior should remain usable during migration
unless Freeze explicitly changes it.

======================================================================
SUCCESS CRITERIA
======================================================================

Initiative succeeds when:

1. RackCad workspace can remain open without blocking AutoCAD.

2. AutoCAD can be used normally while workspace is open.

3. logical rack selection is synchronized into workspace.

4. rack navigation can drive AutoCAD selection/location.

5. browser-like rack sessions work without opening one heavy editor per rack.

6. draft edits persist between tabs but do not touch DWG until Actualizar.

7. stale/external changes are detected before commit.

8. multi-document state is isolated.

9. existing authored/effective authority remains intact.

10. no per-tab AutoCAD event subscription architecture exists.

11. performance is characterized and acceptable.

12. ID3 status is explicitly resolved.
