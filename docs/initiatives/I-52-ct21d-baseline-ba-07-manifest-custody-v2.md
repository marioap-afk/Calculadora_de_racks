## 1. Purpose and threat model

This procedure gives audit integrity to two things: (a) the **baseline record** (the final hash registry BA-11 and this procedure), anchored once when the baseline is complete; (b) the **manifest** of loaded code (E-10, E-11M, E-13), captured later for the exact build and machine (EXEC-11). The manifest attests the enumerable known set only and proves **no isolation** (`NG-13..NG-18`).

| Property | Statement |
|---|---|
| **tamper evidence** | **yes**: accidental change, unrecorded change and rewriting of the custody chain are detectable against the published anchor |
| **non-repudiation and signer identity** | **no**: there is no cryptographic signature and no proof of who acted |
| out of the threat model | a hostile local or repository administrator (`NG-13`); self-review by one person is a declared limit (section 7.1) |
| **declared limitation (remote rewrite)** | branches and tags at the remote can be rewritten or deleted by an account with push rights. A rewrite of the anchor commit or tag is detectable **only** by comparison with an independent copy of the anchor identity (commit SHA and tag object id) kept outside the rewritten references (section 9, step 6). The decisions log inside the same repository is **not** an independent copy |

## 3. Manifest capture (control plane; not executed here)

1. The Coordinator **authorizes** the capture (`AUTHORIZED` custody entry).
2. The **control plane** starts a fresh controlled session on the exact build, machine and profile.
3. The control plane runs the **warm-up** (BA-09 V2) and then the E-10 enumerations and the hasher; the manifest is **generated by the control plane** and is **never hand-edited**.
4. The control plane serializes the manifest canonically (section 4) and computes its SHA-256 (the **manifest identity**).
5. The manifest layers are written to the designated locations (section 2), read-only.
6. The control plane writes a `CAPTURED` custody entry.

## 4. Canonical serialization and hash

| Aspect | Rule |
|---|---|
| format | JSON, UTF-8, LF line endings, no BOM |
| keys | sorted, ordinal |
| numbers | integers in decimal; doubles as in BA-05 V2 section 2.1 if any occur |
| arrays | in the declared order of the schema (module lists sorted by normalized full path, ordinal) |
| hash | SHA-256 of the serialized bytes, lowercase hexadecimal |
| association with the tuple | the manifest hash is a tuple field; a run whose recorded hash differs from the baseline hash is `INVALID` |

## 5. Storage, retrieval and versioning

| Aspect | Rule |
|---|---|
| storage | content-addressed and read-only: `<kind>-<hash>.json` at the designated location |
| retrieval | by hash; the hash is **verified on read**; a mismatch refuses use |
| amendment and versioning | a manifest or a baseline record is **never edited**: a change is a **new capture or a new baseline version** with a new hash and a `supersedes: <hash>` link; superseded items are retained |

## 6. Hash-chained custody log

An **append-only** JSON-lines log. The **genesis entry** (index 0) of the CT-21D custody log is the **baseline record** (`BASELINE_RECORDED`, section 8). Manifest events follow it.

### 6.1 Entry (normative fields)

| Field | Content |
|---|---|
| `index` | integer, 0 for the genesis entry |
| `utc` | UTC time of the entry |
| `role` | `CAPTURE_ROLE`, `REVIEW_ROLE`, `APPROVAL_ROLE` or `CUSTODY_ROLE` |
| `actor` | a person identifier or `CONTROL_PLANE:<build id>` |
| `event` | `BASELINE_RECORDED`, `AUTHORIZED`, `CAPTURED`, `REVIEWED`, `APPROVED`, `ANCHORED`, `IN_USE`, `SUPERSEDED`, `REVOKED` |
| `subjectKind` | `BASELINE` or `MANIFEST` |
| `subjectHash` | for `BASELINE`: the BA-11 seal hash; for `MANIFEST`: the manifest identity |
| `baselineCustodyHash` | only in `BASELINE_RECORDED`: the BA-07 seal hash (this procedure) |
| `prevEntryHash` | the `entryHash` of the previous entry; the genesis entry uses 64 zero digits |
| `anchorRef` | for `ANCHORED` entries: remote, reference, commit SHA, tag name, tag object id; otherwise `null` |
| `note` | free text, may be empty |
| `entryHash` | SHA-256 of the canonical serialization (section 4) of **all other fields** of the entry |

### 6.2 Verification algorithm

1. Recompute every `entryHash`; a difference is a **broken entry**.
2. Check each `prevEntryHash` against the preceding entry; a difference is a **broken chain**.
3. Compare the head `entryHash` with the **anchored** head (section 9); a difference means the log changed after the anchor.
4. Check the state machine of section 7 for every subject; an illegal transition is a **violation**.
5. Compare the anchor commit SHA and tag object id with the **independent copy** of section 9 step 6; a difference means the remote references were rewritten.

## 7. Roles and transitions

| Role | Holds | May not |
|---|---|---|
| `CAPTURE_ROLE` | runs capture **through the control plane** | approve its own capture |
| `REVIEW_ROLE` | the Owner or CAD manager (or a delegate they record): checks the machine-layer entries and the build layer against the build receipt | capture or approve |
| `APPROVAL_ROLE` | the Coordinator: approves a manifest hash, and records the baseline ratifications | capture |
| `CUSTODY_ROLE` | **the Coordinator logical role by default** (designated by this artifact; a change is a new version): keeps the custody log and the anchor | alter an entry already anchored |

```text
BASELINE:  RECORDED (genesis, BASELINE_RECORDED) -> ANCHORED -> [SUPERSEDED by a new baseline version]
MANIFEST:  AUTHORIZED -> CAPTURED -> REVIEWED -> APPROVED -> ANCHORED -> IN_USE -> SUPERSEDED
           any state -> REVOKED (with a recorded cause)
```

- A manifest that is not `ANCHORED` cannot be `IN_USE`. `SUPERSEDED` and `REVOKED` never return to `IN_USE`.
- The `APPROVED` transition and the `ANCHORED` transition are **separate log entries** even when the same person holds the approval and the custody roles.

### 7.1 Multi-role policy (`YES_WITH_ROLE_SEPARATION_IN_LOG`)

One human may hold several logical roles. Requirements: each role transition is a separate log entry; the actor is recorded in every entry; capture is always generated by the control plane; the role multiplicity is disclosed in Owner Act 2 (count of entries by actor and role). Self-review is a declared limit.

## 9. External anchor (procedure; nothing is created here)

The anchor is created **only after**: every baseline artifact is finalized and sealed; BA-11 is complete (every seal hash and every ratification record); every ratification is recorded. **A final anchor is never created earlier.**

| Step | Rule |
|---|---|
| 1 | the `CUSTODY_ROLE` appends the genesis entry (section 8) to the custody log and computes `MANIFEST_CUSTODY_HEADER_HASH` = the `entryHash` of the head entry |
| 2 | it writes the anchor record `docs/automation/evidence/ct21d/baseline-anchor.json` with: `MANIFEST_CUSTODY_HEADER_HASH`, `CUSTODY_LOG_HEAD_INDEX`, the BA-11 seal hash, the BA-07 seal hash, the contract composite hash |
| 3 | the anchor record and the custody log are committed in a **reviewed** commit |
| 4 | the commit is **pushed** to the remote `origin` (`https://github.com/marioap-afk/Calculadora_de_racks.git`) and its presence at the remote is **verified** (`git ls-remote`) |
| 5 | an **annotated tag** `ct21d-baseline/<baseline version>` is created on that commit and pushed; the tag object id is verified at the remote |
| 6 | the anchor identity (commit SHA, tag name, tag object id, remote URL, UTC time) is recorded in an `ANCHORED` custody entry **and** in an **independent copy** outside the rewritten references (the Coordinator's record in the Owner Act 2 package and the evidence of the next gate); the limitation of section 1 applies |

## 10. Audit integrity: what each check protects

| Change | Detected by |
|---|---|
| an artifact or manifest edited in place | the hash is verified on read against BA-11 or the custody log |
| an entry edited in the custody log | recomputation of `entryHash` (6.2 step 1) |
| an entry removed or reordered | chain check (6.2 step 2) |
| the whole log rewritten with a recomputed chain | comparison with the anchored head (6.2 step 3) |
| the anchor commit or tag rewritten at the remote | comparison with the independent copy (6.2 step 5); **not** detectable without it |
| an illegal role transition | state-machine check (6.2 step 4) |
| a manifest used without approval or anchor | `IN_USE` requires `ANCHORED` |
