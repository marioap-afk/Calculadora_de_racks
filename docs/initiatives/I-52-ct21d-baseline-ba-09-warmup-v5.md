## 1. Nature and limits

`WARMUP_SIDE_DATABASE` is **`CONTROL_PLANE_ACTIVITY`** and **`NOT_PRODUCT_MUTATION`** (V2.2 PA-5). The warm-up claims **no isolation** and does **not** authorize a productive warm-up. `PRELOAD_SET` is an operational restriction, not isolation evidence.

## 2. Procedure (numbering of V2.1 13.1; not executed)

| Step | Action |
|---|---|
| 1 | **warm-up** on the `WARMUP_SIDE_DATABASE` (created and owned by the control plane, disposable, never saved, never registered as a document), in the order of section 3; at the end of the step the side database is discarded and every warm-up-only object is released |
| 2 | **record all loads** (assembly snapshot before and after) |
| 3 | **validate the manifest**: every warm-up load belongs to the manifest of the build under test (its build layer is a value of that build's own profile, AR4-06 (2); section 5); otherwise refuse (O1; scenario `NC-WU-FOREIGN`) |
| 4 | **subscribe** E-11M and E-12 (the governed handler instances, created now with their initial sequence numbers) |
| 5 | **capture the E-10 baseline** (two snapshots) |
| 6 | enter the **governed window** |

From step 4 through CP there are no side-database writes by the product or the control plane; the warm-up does not mutate the `LibraryInputRecord` and does not change the library generation id; the seams receive the side database only as an argument; the P-5 guards are unchanged. The subscription code itself runs for the first time at step 4: a load it causes before the baseline is complete makes the baseline invalid and refuses the run (V2.1 13.2, O1); the dry runs of section 4 measure it.

### 3.2 Synthetic warm-up plans (rule; data = W-1)

V2.1 13.1 asks for a synthetic minimal plan per family. This artifact uses, for every family, the plans of the fixture specifications that the governing scenarios use, so that no plan multiplicity of a governing scenario is left out of the warm-up (V2.1 13.1 lists rare plan multiplicities in its residual). The rule: **one plan set per fixture specification of BA-08 V5 section 12.3 that holds a source rack and that a governing scenario uses** (`FX-1F`, `FX-2F`, `FX-4F`, `FX-ANN`, `FX-ANN-BLANK`, `FX-DIM`, `FX-BIG`; `FX-IMP` once K-8 is decided). A variant of BA-08 V5 section 12.5 uses the plan set of its base fixture; `FX-SCRATCH` holds no rack and has no plan set. The plan sets cover every plan-shape class of BA-06 V5 section 10.2 and the largest multiplicities of the catalog.

**Source of the plans (no `mu_k`; D4-06, BA0809V4-05).** The mirrored design `D'` cannot be computed at the bound SHA: no `RACKMIRROR` command and no `mu_k` exist there, and `mu_k` is outside CT-21D (BA-08 V5 section 3 row "commands" and section 11 rule 4). The warm-up plans are therefore **not** `D'`, and they are **not** a `PLAN_CAPTURE_RECORD` (BA-08 V5 section 11.1 defines that record as a per-run capture of PREPARE-R). Each plan set is the set of `HeaderRunPlan`s that the builders of the bound SHA produce for the fixture's **authored source design** (the authored fields of BA-08 V5 sections 12.2 and 12.3): `SelectiveFrontalBuilder.BuildPlan` for the system view of every fondo and the planta builder `SelectivePlantaBuilder` (`src/RackCad.Application/Systems/Selective/` at `3375aadb`), with the catalogs of the bound SHA (BA-08 V5 section 7), and with the logical name replaced by the **synthetic non-blank name `CT21D-WARMUP`**, so that the rack-name label path (where `DrawRackName` is on) and, on the fresh side database, the added-layer path of SL-Y run. These plans need only be **representative**: the per-scenario `WU-DRY` runs measure the coverage of each governing scenario (V2.1 13.1; section 4), so a difference between a warm-up plan and a mirrored plan (for example the mirror flags that `mu_k` sets) is measured there, never assumed away.

**Record (`WARMUP_PLAN_SET`, a warm-up record type of this artifact).** Each plan set is recorded once, offline, as one `WARMUP_PLAN_SET` record:

| Field | Value kind | Content |
|---|---|---|
| `fixture` | string | the fixture id (for example `FX-2F`) |
| `logicalName` | string | `CT21D-WARMUP` |
| `views` | ordered sequence of inline `WARMUP_PLAN_VIEW` records | the frontal of every fondo in ascending `k`, then the planta |

A `WARMUP_PLAN_VIEW` has the fields `viewKind`, `section`, `headers` and `looseInstances`, each encoded exactly as the field of the same name of `PLAN_VIEW` in BA-08 V5 section 11.1 (with its inline `PLAN_GROUP`, `PLAN_PLACEMENT` and `PLAN_INSTANCE` records). The stream is `"CT21D-WUPLAN-V1|" + <record type> + "|" + fields`, with the encoding rules of BA-08 V5 section 11.1 by reference (fields in ordinal order of their names, value kinds, `UNKNOWN` rule); the digest is the SHA-256 of the stream in lowercase hexadecimal. This domain is owned and versioned by this artifact, and it is never the `CT21D-PLANCAP-V1|` domain of BA-08 or the `FPSPEC-V1|EXACT|` domain of BA-05.

**Run-bound fields are synthetic warm-up values, set at replay.** The fields of a `PLAN_CAPTURE_RECORD` that depend on a run are not recorded; the control plane sets them at replay by these rules, and none of them reaches a governed run: `newRackId` = an identifier the control plane mints per plan set at replay, written only to the side database; `effectiveName` = the name computed at replay against the side database's block table (the first creation of a plan takes its requested name and the second the uniquified one, section 3.1 row 1c); `envelopeBytes` = the envelope the control plane composes at replay for each view (the envelope and design document that BA-08 V5 section 12.2 specifies, with the synthetic name and the minted identifier, serialized with `RackEmbedStore` and `SelectivePalletDesignStore`, section 3.1 row 1i); `transform` = the fixed synthetic transform position `(0,0,0)`, rotation `0`, scale `(1,1,1)`, normal `(0,0,1)` (the transform RackCad gives a source reference, BA-08 V5 section 12.2).

The recorded plan sets are **replayed** by the control plane into plan objects in step 1: the warm-up calls **neither the catalog provider nor the builders**. The `WARMUP_PLAN_SET` records and their digests are part of the warm-up definition (V2.1 2.1: warm-up definition version and hash, BUILD_BOUND) and are registered with this artifact before its candidate (W-1). Producing them is offline computation over the bound SHA (no AutoCAD, no host) and needs its own authorization; no plan value is produced or assumed here.

## 4. Coverage criterion and residual (AR3-02, AR3-01, AR3-24, AR4-02, AR4-16)

**`WARMUP_COVERAGE_CRITERION` (per scenario, V2.1 13.1; AR2-42).** The warm-up set is sufficient **for a scenario** when, in the non-governing dry runs **of that scenario**, no assembly-load event occurs inside the governed window after steps 1 to 5, the load events of a designed injection being excluded from the measurement and recorded as the stimulus (AR4-16; "Designed injection loads" below). **No per-family reduction is used**, and no scenario borrows the dry runs of another.

**Which scenarios have dry runs (AR3-02).** A dry-run scenario `WU-DRY-X` is **mandatory for every GOVERNING scenario `X` that enters the governed window**: `RUN_GOVERNANCE = GOVERNING`, `MODE` = `CHARACTERIZATION_RUN` or `VALIDATION`, and `REACH` in `P0..CP` (P0, PL, PR, PP, PW, PS, PV or CP). This includes the scenarios that serve evidence groups; the eleven that V3 left without one are named here: `U-1`, `U-2`, `U-3`, `U-4`, `U-5`, `U-6b`, `U-7`, `U-8`, `S1-SAVE-REOPEN`, `PP-POSTCP` and `CL-CLEANUP-CHECK`. It also includes every other governing scenario of the catalog that meets the rule (for example `CL-CLEAN-FXANNBLANK-FP`, whose dry run is `WU-DRY-CL-CLEAN-FXANNBLANK-FP`). The V3 sentence "every governing host scenario X has its dry-run scenario WU-DRY-X" is **withdrawn**: the rule above replaces it, and BA-04 lists the dry runs it produces. The rule has **no other qualifier**: being in the AR3-01 mode, being a qualification scenario, or running on either build does not exclude a scenario that meets it; a qualification twin `<id>-CB` on the characterization build (AR4-06 (3)) follows the rule like any other scenario.

**Qualification vehicles `Q-I14-*` (ruled by AR4-01, section 217).** Every qualification vehicle `Q-I14-*` is **governing evidence of group Q on the `CHARACTERIZATION_BUILD`** (V2.1 4.3 row I-14): the AR3-01 set applies to the **vehicle**, whose product result is not adjudicated (the verdict comes from the effect records of the writer and of the witness against the independent read). Its product run enters the governed window (`REACH = CP`), so it meets the rule (AR4-01): every qualification vehicle `Q-I14-*` keeps its dry run `WU-DRY-<vehicle>` (the list is the catalog's, informative pointer); the V4 status (`DRAFT`, blocked by AQ-V4-01) is withdrawn. Whether the catalog admits a vehicle that its correction pass added (`Q-I14-P`, open there as AQ-V5-08; BA-04 V5 section 8.2, informative pointer) does not change this rule.

**Declared exclusions (AR3-02).** No dry run is required for: the `NON_GOVERNING_BY_DESIGN` runs (the `WU-DRY-*` themselves, `E4-LEARN-R1-*`, `LK-*`, the four `HDM-CHAR-*` including `HDM-CHAR-FXANNBLANK` (AR4-07), and `EV-L-COMPOSED`, a non-governing composition check (AR4-01)) and the exploratory runs; the **learning** runs (`MODE = LEARNING`, `REACH = LEARN`: the `EV-L-*` micro-scenarios, governing in group E12-L on the `PRODUCT_BUILD`, AR4-01), which are not mirror runs with a governed window; the no-product-run scenarios, qualification scenarios included (`REACH = NONE`, for example `WU-BOUNDARY`); and the synthetic evaluator scenarios (`REACH = SYN`). A qualification scenario with a product run in `P0..CP` is not excluded (the `Q-I14-*` vehicles above).

**Dry-run mode (AR3-01, AR3-02).** Each `WU-DRY-X` runs the plan, fixture specification, injections and designed stimuli of `X` on a private scratch copy of the fixture instance, with `BUILD_UNDER_TEST = CHARACTERIZATION_BUILD` and `RECORDED_NOT_ENFORCED = ["E-03","E-04","E-12 phase A","E-12 phase C","S-1","S-2","S-3"]`: those controls are recorded and do not govern the flow, so the run reaches PV, `Commit()`, V1 and PC wherever the path of `X` does; where the refusal or abort of `X` comes from one of them, the dry run takes that branch through the switch of "Dry-run branches" below (AR4-02). `EXPECTED_PRODUCT_OUTCOME = PROVISIONAL_NON_GOVERNING` (never O1..O7). **`PIN_SLOTS` = only `FIXTURE_INSTANCE` slots**: the fixture of `X` (`FIXTURE_INSTANCE@<FX>`) and, where `X` uses one, its variant library (`FIXTURE_INSTANCE@L-VAR-*`, for example `L-VAR-DIFF` or `L-VAR-PROXY`; BA-04 section 2.1). No EVM, `HOST_DEFAULT_MAP`, E-04 or `LOCK_MODE` pin and no dependency on K-3 (AR3-02: "solo llevan la ranura `FIXTURE_INSTANCE`", read as the pin kind, which the variant libraries share). The measured expectation: **no assembly-load event inside the governed window other than the excluded stimulus loads of a designed injection** (AR4-16, next paragraph; the E-11M log and the E-10 snapshots are recorded).

**Designed injection loads (ruled by AR4-16, section 217; D4-01).** A dry run **excludes from its measurement** the load events of every assembly or module named by a **designed injection** of `X` (a `CANARY_LOAD`, or a `HARNESS_FAULT` that loads a foreign assembly), identified by the identity the injection declares (for an assembly, the E-11M identity of V2.1 13.2: full name, location, module version id, file hash; for a module, the entry identity of V2.1 12.2), and records them **separately as the stimulus**. The criterion counts **every other** load event in the window, including a load that the injected assembly itself causes and that the injection does not name. So the dry runs of the scenarios whose canary load lies inside the governed window by design (for example `NC-E11M-PV`, `NC-E11M-PC`, `AB-AFTER-MUTATION` and `U-5`; BA-04 holds their expectations, informative pointer) measure every load except that of their canary, which the governing run still records as its E-11M violation.

**Dry-run branches (ruled by AR4-02, section 217; closes AQ-V4-02 and W-9).** A `WU-DRY-X` whose source `X` refuses or aborts because of a control of the `RECORDED_NOT_ENFORCED` set takes **the declared branch of `X` at the same checkpoint**, through a switch of the characterization build that records the value of that control and then performs the refusal or abort that `X` declares for that value. The switch is named in the dry run's `PLAN_OR_INPUT` and `INJECTIONS`, and the dry run keeps the `REACH` and the log and event profiles of `X` (BA-04 declares them; its list of sources is `NC-E12A`, `NC-E04-R2`, `NC-E03-NOT-HELD`, `NC-E03-REACQUIRE`, `NC-S1-Y1` and `NC-S1-Y1-SILENT`, informative pointer). For a source whose declared branch is conditional (`NC-E12A`, conditional on delivery through `CER-WIT`, AR4-16), the switch performs the abort only for the recorded value on which `X` declares it, and otherwise the dry run continues as `X` does. The loads of these branches are therefore **measured** by the dry runs of their own scenarios; they are no longer part of the declared residual.

**Count (AR3-24).** Per governing scenario, the number of dry runs is **`WU_DRY_RUNS = N_B`** of `PARAM-01` (BA-10 V5): the Owner fixes `p_B` and `alpha_B` (Q-O2) and the Coordinator records the value; it is **UNSET**. BA-04 applies it; this artifact does not use its value.

**Consequences.** A counted load inside the window of a dry run is a design finding: the warm-up is revised (a new version of this artifact, and so of the baseline: the warm-up definition is a BUILD_BOUND tuple field, V2.1 2.1), adding the path only if it leaves no retained state (V2.2 PA-5 condition 11) or else preloading the dependent assembly. **A warm-up revision never preloads an assembly or module named by an injection** of any scenario (AR4-16): a preloaded canary would no longer be a first-time load in the governed window, and the E-11M negative controls and violations that rely on it would be neutralized. A load inside the governed window of a governing run is an E-11M `FAIL` (class B).

**Declared residual (lazy-load paths).** Error and abort paths not reached by the scenario's own dry runs (the branches of a control of the `RECORDED_NOT_ENFORCED` list are no longer part of it: the dry runs take them through the switch of AR4-02, above); **code differences between the characterization build and the product build** (the dry runs measure the characterization build; the recorded build equivalence of AR4-06 (4), BA-08 V5 section 16.3 K-10 (the record, its content and its custody: BA-07 V5 section 5.3), bounds those differences to what it records (the switches in their declared harness assemblies, or the reviewed diff); the governing run's E-11M still fails on any load in its window); host modules loaded on demand for object types or features; culture resources (the solution has **no** `.resx` or satellite assemblies: evidence `B7` P13); code reachable only during a real document mutation.
